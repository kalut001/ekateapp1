# Gruppo G1 — nucleo, accessi, ruoli, database

Revisore: G1. Sito di test: http://127.0.0.1:8080 (WP 7.1.4, PHP 8.3). Prove reali eseguite con i cookie di /opt/wpt/jars.

## Esito sintetico
Nessun difetto critico di isolamento tra aziende o di privilege escalation nei file assegnati.
L'architettura di sicurezza del nucleo è solida e ben progettata:
- lo smistatore `apac_handle_action` forza per i clienti `azienda_id = apac_user_azienda_id()` (ignora il valore inviato) e tutte le operazioni "cliente" dei miei file filtrano per azienda con `apac_get_row_for_azienda()` o inseriscono con `azienda_id` = propria;
- il nuovo ruolo `apac_collaboratore` (1.28.0) vale come "studio" dentro l'area riservata (per progetto) ma **non** può scalare a amministratore WP;
- l'anteprima "Vedi come il cliente" è solo-GET e non ha effetti server sui POST;
- l'area lavoratore mostra solo i dati propri;
- aggiornamento DB pulito (20→28), tutte InnoDB + utf8mb4.
Rilievi solo di tipo governance/privacy (uninstall mancante, cancellazione del registro attività da parte del collaboratore).

## Difetti / rilievi

### G1-01 | basso | CONFERMATO-codice | manca uninstall.php (ap-area-clienti.php:100-184, assenza file includes/../uninstall.php)
Non esiste `uninstall.php` e `apac_deactivate()` (riga 182-184) ferma solo il cron. Alla
**disinstallazione** del plugin restano: le 53 tabelle `wp_apac_*` (con dati personali dei lavoratori —
`lavoratori`, `firme`, `consensi` con IP/user-agent, `dpi`, foto segnalazioni), tutte le `apac_*` options,
i ruoli `apac_cliente` e `apac_collaboratore`, gli utenti WP creati dal plugin e la cartella privata dei
documenti sul filesystem. 
- Riproduzione: `ls .../uninstall.php` → assente; `register_deactivation_hook` → solo `wp_clear_scheduled_hook`.
- Conseguenza: dati personali (D.Lgs. 81/2008 + GDPR) conservati a tempo indefinito dopo la rimozione del
  plugin; nessuna procedura di cancellazione. Può essere una scelta (dati preziosi), ma andrebbe almeno
  documentata/offerta un'opzione di pulizia.
- Correzione proposta: aggiungere `uninstall.php` con pulizia opzionale (option-gated), o documentare la
  conservazione volontaria.

### G1-02 | basso | CONFERMATO-codice | il collaboratore può cancellare/azzerare il registro attività (operazioni.php:101-102, actions.php:965-991, admin-tools.php:722-731)
`log_voce_delete`, `log_orfani`, `log_svuota` hanno `ruolo = studio`; dato che un `apac_collaboratore` è
"studio" (`apac_is_admin()` true), può eliminare singole voci del registro (`log_voce_delete`, **senza
conferma**) o svuotare l'intero registro (`log_svuota`, con `conferma=ELIMINA`, lascia una sola riga).
Il registro attività è l'unico elemento di accountability sulle azioni dei collaboratori: un collaboratore
può cancellare la traccia delle proprie operazioni (incluse creazioni/eliminazioni di utenti e aziende).
- Conseguenza: perdita della pista di controllo da parte di un ruolo non-amministratore.
- Correzione proposta: riservare `log_svuota`/`log_voce_delete` a `current_user_can('manage_options')`
  (solo amministratore WP), non a `apac_studio`.

### G1-03 | informativo | SOSPETTO (fuori dai miei file) | notice "wpdb::prepare called incorrectly" nel debug.log
Caricando il portale come admin compare in `/opt/wpt/debug.log` il notice
`Function wpdb::prepare was called incorrectly. The query argument ... must have a placeholder.`
Verificato che **nessuno** dei file assegnati chiama `prepare()` senza segnaposto (tutte le occorrenze
multilinea in helpers.php:142/157, actions.php:683, db.php:1226 hanno `%d/%s`). Probabile origine in
portal.php o altro file non assegnato. Segnalato per il gruppo proprietario di quel file.

### G1-04 | informativo | SOSPETTO (fuori dai miei file) — cross-check protocollo | operazioni.php:134-136
`protocollo_nuovo`, `protocollo_annulla`, `protocollo_sostituisci` sono `cliente` + `ambito = nessuno`:
lo smistatore quindi **salta** `apac_can_access_azienda()` e passa all'operazione `azienda_id` = azienda
propria del cliente. Le funzioni `apac_op_protocollo_*` (in `protocollo.php`, non assegnato a G1) devono
perciò filtrare autonomamente il `riga_id`/id del protocollo per `azienda_id` della richiesta e non fidarsi
di un id inviato. Da verificare nel file di competenza (gruppo protocollo). Nei MIEI file non esistono
operazioni `cliente + nessuno` che ricevano id di riga senza filtrare (le uniche `cliente+nessuno` mie,
`guida_chiudi`/`novita_letta`, non toccano righe di altre aziende).

## Prove reali eseguite (riproducibili)

### A. IDOR cross-azienda — cliB (Beta, azienda 2) contro dati di Alfa (azienda 1): BLOCCATO
Ottenuti nonce+once reali dalla pagina `?sez=lavoratori` servita a cliB, poi:
```
curl -b jars/cliB.txt .../admin-post.php \
  -d action=apac_action -d op=lavoratore_save -d azienda_id=1 \
  -d _apac_nonce=<cliB> -d _apac_once=<cliB> \
  -d id=1 -d nome=HACK -d cognome=HACKED-G1 -d codice_fiscale=RSSMRA80A01H501U -d attivo=1
```
Esito: `302 → ...&apac_msg=denied`. Il lavoratore Alfa id=1 resta "Bianchi" (immutato).
Causa: smistatore forza `azienda_id=2`; `apac_get_row_for_azienda('lavoratori',1,2)` → null → `denied`
(actions.php:34-37, 291-294). Stesso schema protegge attestato/documento/scadenza/segnalazione.

### B. apac_collaboratore — tentativi di escalation: TUTTI BLOCCATI
Caps reali di collab (id6): `read, apac_studio, apac_collaboratore` (niente manage_options/edit_posts/list_users).
- `GET /wp-admin/profile.php` → 302 → /area-riservata/ (admin.php:6-20 blocca il collaboratore).
- `GET /wp-admin/user-new.php` → 302 → /area-riservata/.
- `GET /wp-json/wp/v2/users?context=edit` → **401** `rest_forbidden_context` (non può editare utenti).
- `GET /wp-json/wp/v2/users` → solo autori pubblici (id1 admin, nome/slug): comportamento standard di WP,
  non introdotto dal plugin; nessun dato sensibile.
- `GET /wp-admin/options-general.php?page=apac-settings` → **403** (manage_options richiesto).
- collab → `op=utente_revoca` su admin (user_id=1): `302 → apac_msg=denied`; `apac_revocato` di admin resta vuoto.
- collab → `op=utente_reset` su admin (user_id=1): `302 → apac_msg=denied`; nessuna email di reset in mails.log.
Motivo: `utente_create` assegna sempre `role = APAC_ROLE` (actions.php:839); tutte le `utente_*` passano da
`apac_get_client_user()` che esclude admin/studio/editor (actions.php:895-901). Il collaboratore **non** può
creare/promuovere utenti con ruoli WP superiori, né toccare email/password dell'admin, né le impostazioni/SMTP.

### C. Revoca accesso — distrugge le sessioni: CONFERMATO (codice)
`apac_op_utente_revoca` (actions.php:916-920) e `apac_op_lavoratore_accesso`/`apac_lavoratore_revoca_accesso`
(lavoratore-area.php:217-247) chiamano `WP_Session_Tokens::get_instance($uid)->destroy_all()`: l'utente esce
subito. OK.

### D. Aggiornamento DB da versione precedente: PULITO
`wp option update apac_db_version 20` + ricarica di una pagina → riportata a **28** da `apac_maybe_upgrade`
(ap-area-clienti.php:186-201); nessuna `apac_migration_error`; nessun errore/warning/fatal in debug.log
attribuibile al plugin (solo il notice G1-03, non dai miei file). Tutte le 53 tabelle `wp_apac_*`:
`ENGINE=InnoDB`, `TABLE_COLLATION=utf8mb4_*` (emoji OK). `dbDelta` idempotente (CREATE TABLE con `$charset`
da `get_charset_collate()`), indici `azienda_id` presenti su ogni tabella dati, migrazione indice protocollo
`(azienda,anno,numero)` corretta (db.php:1154-1168). Versione riportata a 28 dal plugin (già fatto).

### E. Lint PHP: OK su 7.4 e 8.3
Tutti i 12 file: `php -l` pulito con `php:7.4-cli` (docker) e PHP 8.3 locale. Nessuna funzione solo-PHP8
(`str_contains`/`str_starts_with`/`str_ends_with`/`array_is_list`) in codice dichiarato 7.4+.

## Verifiche fatte che risultano CORRETTE (non difetti)
- **forms.php — valori conservati dopo errore**: il transient è `apac_form_<get_current_user_id()>_<token>`
  (forms.php:49,81,103). Un altro utente, anche con lo stesso `?apac_form=token`, legge una chiave con il
  proprio id → nessun dato. Niente leak cross-utente. Password/nonce esclusi (`apac_form_excluded_keys`).
- **forms.php — apac_next_url / "Salva e continua"**: NON è open redirect. `apac_next_url()` (forms.php:290-302)
  accetta solo URL con host **identico** a `home_url()` e poi applica `wp_validate_redirect()`. `//evil`,
  `http:/evil`, `\\evil`, `http://host@evil`, `//evil.com` → host diverso → scartati; i redirect finali usano
  comunque `wp_safe_redirect`.
- **anteprima.php**: attiva solo `apac_user_studio()`, solo richieste GET non-admin/non-ajax/non-cron
  (anteprima.php:27-28); su `admin-post.php` (`is_admin()` true) `apac_preview_azienda_id()` = 0, quindi i POST
  non sono influenzati. Nessun bypass server; il blocco dei form è solo UX.
- **lavoratore-area.php**: il lavoratore vede solo i propri dati (attestati/DPI/incarichi filtrati per
  `lavoratore_id`; documenti solo `per_lavoratori=1` della sua azienda). `apac_lavoratore_guard`
  (lavoratore-area.php:61-81) nega export/report/template/ver/img/qr e verifica la proprietà delle foto per
  `autore_id`. Lo smistatore limita il lavoratore alle sole op con `lavoratore=true` (actions.php:29-31).
- **documento_delete/update**: il cliente agisce solo sui documenti caricati da lui (`caricato_da ===
  get_current_user_id()`), lo studio su tutti (actions.php:565-571, admin-tools.php:455-461).
- **misura.php**: commento tempi solo per `manage_options` (misura.php:59) — il collaboratore NON lo riceve; nessuna injection (output `wp_json_encode` in commento HTML).
- **helpers.php — apac_redirect/transazioni**: commit/rollback coerenti; file nuovi tracciati e rimossi su
  rollback; email/push/eliminazione file solo dopo commit (helpers.php:518-580, 691-710).

## Non verificato e perché
- Le op `protocollo_*` (cliente+nessuno): logica in `protocollo.php`, non assegnato a G1 — vedi G1-04 per il
  cross-check richiesto al gruppo competente.
- Origine esatta del notice `wpdb::prepare` (G1-03): generato da file non assegnato (portal.php o simili).
- Download file `apac_file`/firma dei documenti per i lavoratori: il controllo di proprietà è in files.php/
  portal.php (non assegnati); `apac_lavoratore_guard` non filtra `apac_file` — da confermare nel file di quei gruppi.
- Non ho tentato la creazione effettiva di un utente cliente da parte del collaboratore (per non lasciare dati):
  il ruolo è `APAC_ROLE` hardcoded in codice (actions.php:839), quindi nessuna possibilità di ruolo WP superiore.
